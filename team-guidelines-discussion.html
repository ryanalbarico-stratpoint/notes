How we work together

A guide for our team discussion on engineering guidelines. We will cover four topics: how we communicate, how we run meetings, how we use AI, and how we handle Git and code.

These guidelines are not here to add extra steps or to check on anyone. They give everyone the same expectations, help us communicate better, and keep our work at a high standard.

Responsiveness and communication

The goal: keep the team talking well, and handle client concerns on time.

What we expect

  • Reply promptly. This covers team messages, emails, and client messages.
  • Clients come first. Look at blockers, urgent requests, and production problems before anything else.
  • Can’t answer yet? Say so. Tell the person you got the message and when you will follow up.
  • Don’t leave people waiting. If someone needs your feedback or decision, answer them.
  • Tell the team before you are away. Set an Out-of-Office (OOO) message and name someone who can handle urgent things.
  • Raise blockers early. Don’t wait until they start to hurt the project timeline.

Tips to stay responsive

Use a separate browser profile for each client. Create a new user (profile) in your browser, so you have two browsers open: one for Stratpoint and one for the client. Each one keeps its own logins, so you stay signed in to both and never mix up accounts.

  • Save a few quick replies. A ready message like “Got it. I’ll update you by [time].” makes it easy to answer right away.

Meeting attendance and participation

The goal: help everyone take responsibility and stay in step with project work and team talks.

What we could expect

  • Be on time and come ready. Read the agenda or the last meeting notes first.
  • Can’t join? Tell the organizer before the meeting. Then catch up from the notes.
  • Take part. Share your update, ask questions, and say so when you disagree or are unsure.
  • Raise blockers in the meeting. Don’t wait until later.
  • End with clear actions. Every action has one owner and a due date.
  • Give the meeting your attention. Close other tabs and chats.

Working in a hybrid setup

Hybrid work is a blessing. Let’s not take it for granted, and let’s not use it as a reason to get too relaxed.

  • Answer emails and chat within office hours. We are expected to reply to mails and chat messages during office hours, wherever we work from.
  • Be easy to reach. Working from home is still work time. Stay online and keep your chat and email open.
  • Give the same effort at home as in the office. Our work, our meetings, and our updates should be the same.
  • Tell the team before you step away. If you will be unavailable for a while, let them know in advance.

Tips to help you show up

  • Add every meeting to your calendar. Accept the invite so it shows on your calendar, and keep the meeting link in the event.
  • Set reminders and alarms. Use a calendar reminder before each meeting. For client meetings or early ones, set an alarm on your phone too.
  • Block time to prepare. Put a short slot before the meeting to read the agenda and the last notes.
  • Update your calendar when plans change. If you can’t attend, decline early with a short note so the organizer can plan.

Responsible AI use

The goal: use AI as a helper, not a replacement for your own thinking. You stay in charge of the engineering. You should understand your work, and you are responsible for it.

AI-assisted, not AI-done.

AI helps you move faster. The thinking, the decisions, and the final result are still yours.

A

Understand what AI gives you

  • Read and understand all AI-made code, documents, and advice before you use them.
  • Never copy and paste AI code into the project without checking it.
  • Be ready to explain how it works and why you chose it.
  • Check it for correctness, security, speed, and how easy it is to maintain.
B

Follow the project requirements

  • Make sure the output meets the project’s Acceptance Criteria (AC).
  • Check it against business rules, technical requirements, and coding standards.
  • “It works” or “the basic tests pass” does not mean it is right.
C

AI helps, you decide

  • Use AI to support coding, troubleshooting, and learning.
  • Thinking, technical decisions, and final deliverables stay with the developer.
  • You are responsible for the quality, reliability, and maintainability of your work.
D

Follow the client’s AI rules

  • Know the client’s AI policy and follow it.
  • If the client bans or limits AI, don’t use AI tools on that project.
  • Never put confidential client information, source code, credentials, or sensitive data into AI tools that are not approved.
  • Not sure what is allowed? Ask the project lead or manager first.

Keep AI traces out of Git

AI tools often leave files in your project, like configuration files, commands, agent files, and notes. These should not end up in the repository.

  • Remove the traces of AI agents from your project before you commit. This includes AI configuration files, custom commands, agent files, and anything similar.
  • Examples: the .claude, .opencode, or .cursor directories, where agents and commands are stored.
  • Config files like mcp.json and opencode.json.
  • Add them to .gitignore so they are never added to a commit.
  • Check git status before you commit. Make sure only the files for your task are there.
Example .gitignore entries
# AI agent files (use the names your tools create)
.claude/
.opencode/
.cursor/
mcp.json
opencode.json

Commit and push by yourself, not the AI

AI can help you write the code. You are the one who commits and pushes it. Do not let AI agents run Git commit and push on their own. Review the changes, then commit and push them yourself.

Fine to ask AI for

  • Help writing and fixing code
  • A review of your changes
  • Ideas for a commit message

Keep for the developer

  • Reviewing the final changes
  • Running git commit
  • Running git push

Why? Git activity is recorded in the git logs. They show who changed what, and every commit carries your name. Owning your code matters: you check what goes in, and you stand behind it.

“AI can help us write, review, and improve our code, but committing and pushing changes should remain a developer-controlled activity. These actions are recorded in the Git logs, so we need to maintain transparency, traceability, and accountability for every change we introduce into the repository.”

In simple words: AI can help you write the code. You are the one who commits and pushes it, because your name is on the git log.

Follow your project’s standards

Always follow your project’s own standards first, such as how it names branches and writes commit messages. If your project has none, use Stratpoint’s standards. See Git standards and code quality for branch names, pull requests, and commit messages.

This applies to AI-written work too. If AI suggests a branch name or a commit message, change it to match the standard.

Don’t commit them. Add them to .gitignore. If Git already tracks them, remove them from tracking first.

Git standards and code quality

The goal: build the same good habits across projects, while respecting each project’s own standards, workflow, and client needs.

Every project has its own tech stack, client rules, and ways of working. Always follow your project’s existing standards first. If your project has none, use Stratpoint’s standards below. They are the shared baseline we are building.

Branch names

  • Follow the agreed naming rules. They keep the repo tidy and show what each branch is for.
  • If your project already has its own rule, use that one. If it has none, use the Stratpoint format below.
  • Avoid vague names like test, changes, or new-feature.
New feature
feat/<epic-feature-module>-<short-description>-<developer-branch>
Bug fix
fix/<ticket_number>/<short-description>

Configuration and environments

  • Don’t hard-code settings. Keep configuration values outside the application code.
  • Keep environments separate. Development, Staging, and Production each have their own settings.
  • Use environment variables, or the approach your project has approved.
  • Never commit environment files that contain secrets.
  • Follow your project’s secrets management practice.

Avoid

const apiKey = "abc123-secret-key";

Better

const apiKey = process.env.API_KEY;

Commits and pushes

  • Review your changes before you stage and commit.
  • Write clear commit messages that say what changed. Use the format below.
  • Commit only what belongs to the task.
  • Run the required checks and tests before you push.
  • Push only to the right feature or development branch.
  • Don’t push directly to protected or production branches, unless you are clearly allowed to.
  • Don’t force-push a shared branch without agreeing with the team first.

Commit message format

Write your commit message in this format:

Format
type(scope): short description
  • type says what kind of change it is. For example, feat for a new feature, fix for a bug fix, doc for documentation, and chore for small upkeep work.
  • scope is the module or area you changed, like home, auth, or navigation.
  • short description says what changed. You can add the ticket number at the end, like (TASK-010).

Examples

doc(home): add local setup steps to the README
feat(home): consolidate update customer information into a 13-field AMS_CUSTOMER editor
feat(auth): add unit tests for PermissionGuard and AMSSecurityClient (TASK-010)
fix(navigation): close dropdowns on keyboard focus-out
chore(home): update example message

Avoid

update
fixed stuff
changes

Wrap-up

What we want everyone to remember.

  • Communication. Reply on time, put clients first, and raise blockers early.
  • Meetings. Show up ready, take part, and leave with clear actions.
  • AI. AI helps. You understand it, check it, and own the result. You commit and push yourself, and you keep AI files out of Git.
  • Git and code. Follow your project’s standards, or Stratpoint’s if there are none. Keep changes small and clean, and keep secrets out.

We are responsible not only for the code we write, but also for how we communicate, work together, and deliver value to our clients.

Let’s apply these practices the same way across our projects.
